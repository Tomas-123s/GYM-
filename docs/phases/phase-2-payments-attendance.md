# المرحلة 2 — المدفوعات والحضور (الأيام 7–9)

**الهدف:** تسجيل مالي قابل للتدقيق وحضور يومي صحيح حتى مع الطلبات المتزامنة.

## المهام

### المدفوعات والأرصدة
- [ ] إنشاء Payment مع اشتراك، مبلغ decimal موجب، طريقة الدفع، وقت الدفع، مرجع فريد، المستخدم المسجل وملاحظات.
- [ ] تنفيذ تسجيل دفعات جزئية وربطها بالاشتراك؛ استخراج الإجمالي المدفوع والرصيد وحالة Unpaid/Partial/Paid من بيانات الخادم.
- [ ] تعريف سياسة استرداد/تسوية قابلة للتدقيق (لا حذف/تعديل صامت للدفعات المعتمدة)؛ تنفيذها إن دخلت ضمن MVP العملي.
- [ ] منع تجاوز صافي الدفعات المستحق ما لم يعتمد دعم رصيد دائن؛ فحص ذلك في منطق الخدمة ومعاملة قاعدة البيانات.
- [ ] ضمان ذرية تسجيل الدفعة وحساب الأرصدة وتوليد/التحقق من المرجع.
- [ ] تنفيذ سجل دفعات العضو والفلاتر بالتاريخ والطريقة، وتقييد جميع مسارات المال بـAdmin.
- [ ] بناء واجهة تسجيل دفعة جزئية، الرصيد المتبقي وسجل الدفع.

### الحضور
- [ ] إنشاء AttendanceRecord مع `AttendanceDate` منفصل عن `CheckInAt`، والمستخدم المسجل وسبب تجاوز اختياري.
- [ ] فرض `UNIQUE(MemberId, AttendanceDate)` في SQL Server لمنع التكرار حتى عند التزامن.
- [ ] البحث عن العضو بالكود/الهاتف، والتحقق من صلاحية اشتراكه قبل التسجيل.
- [ ] السماح بتجاوز Admin فقط مع سبب ومستخدم مسؤول محفوظين؛ تسجيل التصحيحات كتغييرات مدققة.
- [ ] إرجاع رسالة تعارض واضحة عند حضور مكرر أو اشتراك غير صالح.
- [ ] توفير سجل وفلاتر تاريخ/عضو وواجهة check-in.

### تحقق مرحلي
- [ ] اختبار سيناريو 1200 جنيه: 700 ثم 500، الرصيد 500 ثم صفر والحالة Paid.
- [ ] اختبار مبلغ صفري/سالب، دفعة زائدة، مرجع مكرر، فشل جزئي للمعاملة وصلاحيات Coach.
- [ ] اختبار محاولتي check-in متزامنتين؛ واحدة فقط تُسجل، مع اختبار حدود اليوم حسب منطقة النادي.

## معيار الإنجاز

الحسابات صحيحة ومحسوبة في الخلفية، والسجلات المالية لا تمحى، والحضور غير المكرر مضمون بقيد قاعدة البيانات لا بفحص الواجهة فقط.
